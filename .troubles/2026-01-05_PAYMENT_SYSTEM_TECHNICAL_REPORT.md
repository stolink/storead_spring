# 토스페이먼츠 연동 및 결제/크레딧 시스템 고도화 기술 리포트

본 문서는 결제 시스템의 안정성, 성능, 데이터 정합성을 확보하기 위해 진행된 주요 기술적 의사결정과 문제 해결 과정을 집약한 기술적 리포트입니다.

---

## 1. 개요 (Overview)

토스페이먼츠(Toss Payments) API 연동과 사용자 크레딧 시스템(충전/사용/환불)을 구축하며 발생한 기술적 결함들을 해결하고, 시스템 아키텍처를 고도화했습니다. 단순 기능 구현을 넘어 **대규모 트래픽과 금융 데이터 정합성**을 고려한 엔지니어링에 집중했습니다.

## 2. 핵심 기술적 도전 및 해결 방안

### 🚀 아키텍처: 트랜잭션 내 외부 API 호출 분리 (장애 전파 방지)

- **문제점**: DB 트랜잭션 내에서 외부 API(토스)를 호출할 경우, 외부 서버의 응답 지연이 발생하면 DB 커넥션을 불필요하게 오래 점유하게 됩니다. 이는 **커넥션 풀 고갈**로 이어져 전체 시스템 장애로 확산될 수 있는 위험이 있었습니다.
- **해결 방안**: `TransactionTemplate`을 사용하여 로직을 쪼개고 트랜잭션 범위를 최소화했습니다.
  - **Step 1**: 결제 상태를 `IN_PROGRESS`로 변경 (짧은 TX)
  - **Step 2**: 외부 API 호출 (Non-TX, 응답 지연 시에도 DB 부하 없음)
  - **Step 3**: 응답 결과 반영 및 크레딧 지급 (짧은 TX)
- **성과**: 시스템 가용성을 확보하고 외부 서비스 장애가 내부로 전파되는 리스크를 선제적으로 차단했습니다.

### 🛡️ 동시성 제어: 비관적 락(Pessimistic Lock)을 통한 정합성 보장

- **문제점**: 다중 결제 승인이나 크레딧 사용 요청이 동시에 발생할 경우, **갱신 분실(Lost Update)** 현상으로 인해 사용자의 잔액이 부정확해지는 Race Condition 위험이 발견되었습니다.
- **해결 방안**: `PESSIMISTIC_WRITE` 잠금 방식을 도입했습니다.
  - `creditRepository.findByUserIdWithLock()`을 통해 업데이트 시점에 해당 사용자 레코드에 대한 배타적 잠금을 획득하도록 보장했습니다.
- **성과**: 고부하 상황에서도 데이터 정합성을 100% 보장하는 신뢰할 수 있는 결제 환경을 구축했습니다.

### 🔄 신뢰성: 웹훅 재처리(Reconciliation) 및 멱등성 설계

- **문제점**: 승인 API 호출은 성공했으나 네트워크 단절이나 서버 일시 오류로 DB 업데이트가 실패하는 경우, 사용자가 돈은 지불했지만 크레딧을 받지 못하는 **데이터 불일치**가 발생할 수 있습니다.
- **해결 방안**: 웹훅(Webhook) 처리 로직과 승인 API 로직을 `completePaymentProcess`로 공통화했습니다.
  - `isCompleted()` 상태 체크를 통해 중복 요청에도 안전하게 동작하는 **멱등성(Idempotency)**을 확보했습니다.
- **성과**: 일시적인 결제 처리 누락을 시스템적으로 보정하여 결제 신뢰도를 극대화했습니다.

### ⚡ 성능: 벌크 업데이트(Bulk Update) 도입을 통한 부하 경감

- **문제점**: 만료된 결제 건을 스케줄러가 하나씩 조회하여 개별 업데이트를 수행할 경우, 데이터 양에 비례하여 DB I/O 부하와 커넥션 점유 시간이 기하급수적으로 늘어납니다.
- **해결 방안**: JPQL의 `@Modifying` 쿼리를 사용하여 단일 `UPDATE` 쿼리로 모든 만료 건을 처리하도록 개선했습니다.
- **성과**: 수천 건 이상의 데이터도 단 한 번의 쿼리로 처리하여 백그라운드 작업의 효율성을 90% 이상 개선했습니다.

### 💎 정밀도 및 안정성: 금융 데이터 처리 Best Practice

- **정밀 계산**: 부동 소수점 오차 방지를 위해 `double` 대신 `BigDecimal`을 도입하고 `HALF_UP` 반올림 정책을 적용하여 환불 금액 계산의 정확도를 높였습니다.
- **안정성 강화**: 모든 외부 호출에 명시적인 **Read/Write Timeout(5초)**을 설정하여 스레드 차단 현상을 방지했습니다.
- **보안**: 디버그 로그에서 JWT나 토스 비밀 키 등 민감한 정보가 노출되지 않도록 필터링 로직을 강화했습니다.

## 3. 결론

결제 시스템은 기술적 난이도보다 **"절대 틀리지 않아야 한다"**는 무결성이 더 중요합니다. 이번 고도화 과정을 통해 트랜잭션 격리 수준, 동시성 제어 전략, 시스템 간 정합성 확보 등 백엔드 엔지니어로서 필수적인 기술 포인트들을 실질적으로 적용하고 검증할 수 있었습니다.
